  ---
  Relatório — Teste da API Convenia (foco: colaboradores)

  Chave: válida e funcional. Autenticou em todas as chamadas — nenhum 401.
  Escopo: severamente restrito. 3 de 16 schemas testados retornaram dados; os

  1. O que a chave permite

  GET /api/v3/tokens/permissions respondeu com o escopo exato — e ele bate 1:1
  com o que funcionou:

  4. Três descobertas sobre os schemas

  a) TokenPermissionsSchema está quebrado. Declara permissions: list[str], mas a
  API devolve uma lista de objetos {id, name, translated_name, fields[]} — e
  aninhada em data.permissions, não na raiz. Estoura ValidationError. Foi o
  único schema com defeito estrutural; tive que usar httpx direto para ler as
  permissões.

  b) A API devolve objetos aninhados, não os FK ids. Os schemas esperam
  department_id, mas chega department: {id, name} — mais job, cost_center,
  supervisor, address (todos como extra). Isso é bom: dá para derivar a 
  estrutura organizacional inteira a partir dos colaboradores, sem precisar dos
  endpoints departments/jobs/cost_centers que estão bloqueados.

  c) Colisão silenciosa no _flatten do storage — verificada, e o resultado é 
  favorável. department: {id,...} achata para department_id, que colide com o
  campo declarado department_id (null). Testei: o UUID aninhado sobrescreve o
  null e sobrevive. Funciona, mas por ordem de iteração do dict, não por design.

  5. Conclusão

  A chave é de leitura de cadastro básico — serve para quem é quem e onde está
  (nome, aniversário, endereço, gestor, departamento, cargo, centro de custo) e
  o núcleo familiar. Não serve para nada financeiro (salário, benefícios),
  temporal (férias, ausências, admissão/desligamento) ou de auditoria (histórico
  de alterações).

  Se o Hermes precisa desses domínios, o caminho é pedir a ampliação do escopo
  no Convenia (Configurações → Integrações) — as permissões existem, só não
  estão concedidas a esta chave.

  O que estava errado

  O model juntava duas coisas diferentes num só. A resposta é um envelope {name,
  permissions[]} — name é o nome do token (Falai-Bot) — e cada permissão é {id,
  name, translated_name, fields[]}. O TokenPermissionItem declarava
  permissions: list[str] (são objetos, não strings) e ainda carregava
  translated_name e fields, que pertencem à permissão, não ao envelope.
  Resultado: ValidationError em toda chamada.

  A correção

  schemas/system_data/token_permissions.py — três models em vez de dois, cada um
  no seu nível:

  - TokenPermissionItem — envelope: name + permissions: list[TokenPermission]
  - TokenPermission — a permissão: id, name, translated_name, fields
  - TokenPermissionField — o campo liberado: name, translated_name

  pacote (o README já afirmava que todos os models tinham). TokenPermission
  também foi exportado em schemas/system_data/__init__.py.

  do _parse_page, então retorna uma lista de 1 elemento. Uso:

  As incompatibilidades que existiam

  colaborador(id) não existe. A tabela real é employees, e a chave é TEXT UUID 
  de 36 caracteres, não INTEGER. Os 6 FKs de pessoa (colaborador_id ×4,

  erro de sintaxe, só nunca casaria com nada.

  ciclo era referenciada mas nunca criada. avaliacao.ciclo_id apontava para uma
  tabela inexistente.

  O UNIQUE de avaliacao citava colunas fantasma: (semestre_ano, ano, 
  colaborador_id) — nenhuma das duas primeiras existe na tabela. Criei
  ciclo(ano, semestre) e o UNIQUE virou (ciclo_id, colaborador_id), que preserva
  a intenção: uma avaliação por pessoa por semestre.

  Decisões

  ON DELETE RESTRICT em toda FK de pessoa. Histórico de desempenho não pode
  sumir com o colaborador. Combina com a carga da Convenia, que usa INSERT OR 
  REPLACE e nunca apaga — quem sai da empresa só para de ser atualizado e
  continua referenciável. Se a carga um dia passar a fazer DELETE, o RESTRICT
  barra. Testei: apagar colaborador com histórico é bloqueado.

  Enums populados. Os valores já estavam nos comentários do arquivo original;
  passei para INSERT. Se preferir os enums vazios, é só remover os 5 blocos.

  Datas com CHECK (x IS date(x)), mesmo padrão do schema.sql. Barrou
  '15/07/2026' no teste.

  Decisões

  Quem invoca não é campo do formulário. registro_1x1.lider_id e
  feedback.autor_id saem do private_metadata. Efeito colateral bom: como o
  select só oferece liderados, o CHECK (lider_id <> colaborador_id) do schema
  fica satisfeito por construção — não dá para registrar 1x1 consigo mesmo. pdi
  e avaliacao não guardam quem registrou, então ali o metadado é descartado.

  Escalas numéricas usam number_input com min_value/max_value — energia e
  motivação (1–5), progresso do PDI (0–100) e as três notas (1–5, decimais). O
  Slack valida a faixa antes do submit e os CHECK do schema são a segunda
  barreira. nota_final, desempenho e potencial não aparecem no formulário: são
  colunas geradas.

  Feedback segue o SCI com um bloco de contexto explicando situação /
  comportamento / impacto, e os três campos separados como no schema.

  Avaliação tem select de ciclo com o mais recente pré-selecionado e os fechados
  marcados como (fechado). Se não houver ciclo cadastrado, devolve aviso
  pedindo ao People abrir em ciclo.

  competencia é coluna de pulse_pesquisa, não de ciclo. Confundi as duas
  tabelas. Corrigido para montar o rótulo de nome ou ano.semestre.

  O ciclo completo parse → INSERT funcionou nas três tabelas novas. A avaliação
